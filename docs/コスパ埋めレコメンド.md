# コスパ埋めレコメンド（Fill Recommendation）

「次に何を埋めると総合 BEAT-PT が一番伸びるか」を **期待値** で出して降順に並べる機能。
既存の「ランクアップアドバイス」（ダッシュボード下部のパネル）の中身を、この期待値ベースの推薦に置き換えた。

- Backend: `backend/src/main/java/com/beatseeker/backend/service/FillRecommendationService.java`
- API: `GET /api/analysis/fill-recommendation`（`ChartTendencyController`）
- Frontend: `frontend/src/components/RankUpAdvice.vue`
- Test: `backend/src/test/java/com/beatseeker/backend/service/FillRecommendationMathTest.java`

---

## 1. なぜ作ったか

旧ランクアップアドバイスには 2 つの穴があった。

| 穴 | 中身 |
|----|------|
| **未プレイ譜面を提案できない** | 候補が `flatScores`（＝プレイ済み譜面のみ）で、さらに伸びしろ API も「自分が A 以上で出している譜面」しか返さない。IIDX プレイヤーが実際に一番やる「☆12 を 1 曲埋めて TOP100 の 100 位を押し出す」を提案できなかった。 |
| **予測を確定値として扱う** | 伸びしろ API の予測スコアを「確実に出せる上限」と決め打ちし、`ptGain / scoreIncrease` の効率順に並べていた。外す確率をまったく見ていないので、「理屈上はコスパ最強だが実際には取れない譜面」が上位に来る。 |

sp12 埋めシートや V-ARCHIVE は「埋まっているか／いないか」の一覧であって、
「どれから埋めれば一番伸びるか」は出してくれない。ここが差別化点になる。

## 2. 計算式

依頼された定式化は

```
∂BEAT-PT/∂スコア × P(達成 | 推定能力)
```

だが、これはスコア軸で積分すると期待獲得 pt そのものになる（部分積分）。

```
E[ΔBEAT-PT] = ∫_{s*}^{∞} (∂BEAT-PT/∂s) · P(S ≥ s) ds
            = E[ max(0, pt(S) − baseline) ]
```

- `S` … 推定能力から見た「その譜面で最終的に出せるスコア」の確率変数
- `pt(s)` … 単曲 BEAT-PT（`BeatPtCalculator.calculatePoints`）
- `s*` … 損益分岐スコア（`pt(s*) = baseline` となるスコア）

実装は **右辺（期待値そのもの）** を数値積分する。
BEAT-PT は AA / AAA / MAX- で weight × 1% ずつ不連続に跳ねるので、
左辺を 1 点の微分で近似するとボーナス段差を取りこぼす。分布を刻んで `pt` をそのまま評価すれば段差も拾える。

### baseline（何と比べた増分か）

総合 BEAT-PT は **上位 100 譜面の合計** なので、増分は TOP100 の出入りで決まる。

| 譜面の状態 | baseline | 意味 |
|-----------|----------|------|
| TOP100 圏内 | その譜面の現在 pt | 純粋な上積み |
| TOP100 圏外・未プレイ | 100 位の pt | ここを超えて初めて合計に効く |

`P(S ≥ s*)` が `achieveProbability` = 「この譜面を触る価値がそもそもあるか」の確率。
未プレイ譜面ではこれが「埋めて 100 位を押し出せる確率」そのものになる。

### 能力推定（S の分布）

`PairRegressionService` の譜面ペア回帰（logit 空間の単回帰、|r| ≧ 0.90 のペアのみ）をそのまま流用する。
参照譜面 A ごとの予測 `ŷ_A = slope·logit(A) + intercept` を重み `w(r)` で加重平均して μ とし、分散は 2 成分の和で置く。

```
σ² = σ_resid²                 … その譜面固有の相性（参照を増やしても消えない）
   + σ_between² · Σw²/(Σw)²   … 参照譜面どうしの食い違い（加重平均の標準誤差）
```

- `σ_resid` … ペアごとの残差 sd（`sdY·√(1−r²)`）の加重平均。回帰キャッシュに `Reg.sdY` を追加して取れるようにした。
- `S` は logit 空間で正規分布とみなす。スコアレートは 0〜1 に飽和するので、生スコア空間の正規分布より実態に合う。
- σ は `[0.04, 1.2]`（logit）にクランプ。下限は「参照が偶然揃っただけで確率 100% と言い切る」のを防ぐため、上限は参照の乏しい高難度譜面に期待値が張り付くのを防ぐため。

参照譜面の数（`supportCount`）が 3 未満の譜面はペア回帰では予測を出さない。
|r| ≧ 0.95 だけで足りれば `accuracy = HIGH`、0.90 まで緩めて足りたら `LOW`。
この 2 段構えは伸びしろランキング（`computeGrowthPotential`）と同じ基準で、
両機能の「予測が出る／出ない」の境界を揃えてある。

### 枯渇対策: 加法モデルによるフォールバック（BASE / RANK）

ペア回帰は「両方を A 以上でプレイした人が 30 人以上」のペアしか使えないので、
不人気曲や稼働直後の新曲は候補から丸ごと抜け、提案が枯渇する原因になっていた。
そこで `PairRegressionService.rebuild()` で同じスコアから **加法モデル** も同時に推定する。

```
logit(score_uc) = θ_u + δ_c + ε        θ_u: ユーザー実力、δ_c: 譜面効果
```

- 推定は交互平均（θ を固定して δ を平均 → δ を固定して θ を平均）を 8 回。スコア数万行で数十 ms。
- δ_c は「その譜面をプレイした人」だけで立つので、1 人でもプレイしていれば足場ができる。
- θ_u はキャッシュ側の値を使わず、リクエストごとに自分の参照譜面（A 以上）の `logit − δ_c` の平均で引き直す（δ_c が 5 人以上で立っている譜面のみ）。1 譜面あれば推定し、参照が少ないぶんは `Var(θ_u) = max(参照間分散, s_pool²) / n` で σ に反映する。

候補ごとの予測は次の 4 段で決める。下の段ほど σ が大きいので、達成率順に並べると自然に後ろへ回る。

| 段 | `accuracy` | 条件 | μ | σ² |
|----|-----------|------|---|----|
| 1 | `HIGH` | ペア回帰 \|r\| ≧ 0.95 が 3 参照以上 | 加重平均 | 残差² + 参照間ばらつき |
| 2 | `LOW` | ペア回帰 \|r\| ≧ 0.90 が 3 参照以上 | 同上 | 同上 |
| 3 | `BASE` | δ_c が 5 人以上で立っている | θ_u + δ_c | s_c² + s_c²/n_c + Var(θ_u) |
| 4 | `RANK` | 難易度表の同ランクに δ が立った譜面がある | θ_u + mean δ(同ランク) | s_pool² + Var_rank(δ) + Var(θ_u) |

- `s_c` は譜面の残差 sd をプール値 `s_pool` へ縮約したもの（仮想サンプル 10）。
- `Var_rank(δ)` は同ランク内の δ の分散。「そのランクのどの譜面かが分からない」ぶんの不確実性。
- 難易度表に載っている Lv11+ の ANOTHER / LEGGENDARIA は、θ_u が立つ限り必ずいずれかの段で予測が付く。
- 選択バイアス（難曲ほど強い人が選んでプレイする）はペア回帰と同じく残る。フォールバックとして許容する。
- フロントは `BASE` / `RANK` に「概算」バッジを付けて区別する。

### クランプ

- 上限はコミュニティ実測最高（`communityMaxByKey`）。誰も出していないスコアは提示しない。
- 下限は現在スコア。自己ベストを下回る引きは更新にならないので増分 0 として扱う。

## 3. API

### `GET /api/analysis/fill-recommendation?gap=12.3`（要ログイン）

`gap` はフロントが表示している「次ランクまでの残り pt」。省略時はサーバー側の副ティア境界
（`BeatTierScale.nextSubTierOf`）から求める。フロントの BEAT-PT 計算と一致させるため、通常は渡す。

```jsonc
{
  "top100Threshold": 152.3,     // 100 位の pt（押し出しライン）
  "totalBeatPt": 15840.2,       // 上位 100 譜面の合計
  "scoredChartCount": 412,      // pt が付いている譜面数
  "referenceChartCount": 380,   // 能力推定に使えた参照譜面数
  "nextTierGap": 12.3,          // 次ランクまでの差分（gap 指定時はその値）
  "nextTierLabel": "Master IV", // gap 未指定時のみ。次の副ティア名
  "cumulativeExpectedGain": 13.1, // 返した items の期待値合計
  "gapCovered": true,           // 合計が差分に届いたか。false なら候補が足りない（枯渇）
  "candidateCount": 640,        // 予測が付いた候補数（打ち切り前）
  "noPredictionCount": 0,       // 4 段すべてで予測できなかった譜面数
  "tierCounts": { "HIGH": 210, "LOW": 95, "BASE": 300, "RANK": 35 },
  "items": [
    {
      "title": "...", "difficultyName": "ANOTHER",
      "informalRank": "12.3", "difficultyLevel": 12,
      "unplayed": true,          // 純粋な「埋め」候補
      "currentScore": 0, "currentRate": 0.0, "currentBeatPt": 0.0,
      "inTop100": false,
      "maxScore": 2380,
      "predictedScore": 2140.5, "predictedRate": 89.94, "sigmaRate": 0.83,
      "breakEvenScore": 2098,    // ここを超えて初めて合計 pt が増える
      "achieveProbability": 0.71,
      "targetScore": 2116, "targetRate": 88.91,
      "targetLabel": "AAA", "targetProbability": 0.63, "targetGain": 3.2,
      "expectedGain": 2.4,       // 期待獲得 pt
      "supportCount": 34, "accuracy": "HIGH"   // accuracy: HIGH / LOW / BASE / RANK
    }
  ]
}
```

`items` は **達成率（`achieveProbability`）降順**。表示は 1% 刻みなので同じ % なら `expectedGain` 降順。
先頭から `expectedGain` を足して `gap` に届いた所で打ち切る（届かなければ全件、`gap ≦ 0` なら 300 件）。
`expectedGain < 0.05` の候補は返さない。

管理者は `GET /api/admin/fill-recommendation?userId=...&gap=...` で任意ユーザーぶんを引ける（推薦精度の検証用）。

## 4. フロント

`RankUpAdvice.vue` は残り pt を `gap` として API に渡し、返った候補を **10 件ずつ** 表示する。
候補は達成率順に「次のランクに届くまで」並んでいるので、「さらに表示（あと n 件）」を開き切れば
必要な曲がすべて見える。候補評価・ボーダー探索・TOP100 判定はすべてバックエンドへ寄せてある。

表示するもの:

- `埋め` バッジ（`unplayed`）と青系の背景 — 未プレイ譜面がひと目で分かる
- `概算` バッジ（`accuracy` が BASE / RANK）— ペア回帰の参照が無く、加法モデルで推定した候補
- 狙い目ボーダー（`targetLabel`）と目標スコア・レート
- `達成率 xx%`（`achieveProbability`）— 70% 以上は緑、40% 未満は琥珀
- `期待 +x.x pt`（`expectedGain`）
- 合計の期待値と、次ランクまでの残り pt の対比（届かなければ「不足」）

厳密には 1 曲埋めるたびに 100 位ラインが上がって後続の期待値は少し下がるが、
「次に触る曲」を決める目安なので独立に足し合わせている。

## 5. コスト

重いのは `PairRegressionService` の全ペア回帰キャッシュ構築（全体で 1 本）だけで、これは既存の伸びしろランキングと共用。
ユーザーごとの計算はキャッシュ参照のみで、参照譜面 A 側から疎な回帰マップを引くので
「候補譜面数 × 参照譜面数」の空振りが出ない（`PairRegressionService.getRegressionsFrom`）。
曲マスタ・難易度表は 10 分だけ `FillRecommendationService` にメモリ保持して使い回す。

### キャッシュ構築のタイミングと負荷対策（2026-09-07）

本番の `scores` は 264 万行・835 MB で、構築用の全スコア取得は全表走査（サーバー側 12 秒）で 70 万行を返す。
以前はリクエストスレッドで初回構築していたため、Hibernate の `List<Map>` 展開（一時 250 MB 前後）で
小さいヒープでは GC が走り、接続既定の `statement_timeout = 30s`（Hikari の init SQL）に掛かって
500 になった。対策は次の 3 点。

| 対策 | 内容 |
|------|------|
| ストリーミング受信 | JdbcTemplate の `fetchSize = 5000` でカーソル読みし、行を packed `long[]` へ直接詰める。同じ譜面の重複行（source 違い）は最大スコア 1 本に潰す |
| タイムアウト緩和 | 構築トランザクション内だけ `SET LOCAL statement_timeout = '120s'`（PostgreSQL のときのみ。他 API の 30 秒は変えない） |
| 日次バッチ化 | 起動完了時と毎日 04:30 JST にバックグラウンドで構築。未構築の間は API が **503 + `retryAfterSec`** を返し、フロントは「計算中」のまま自動再試行する |

管理者は `GET /api/admin/pair-regression/status` で状態を見られ、`POST /api/admin/pair-regression/rebuild` で日次を待たずに再構築できる。
`prod-db` プロファイル（`app.scheduling.enabled=false`）では日次は動かないが、起動時構築は動く。

## 6. 検証

`FillRecommendationMathTest` が DB 非依存で次を押さえている。

- 標準正規 CDF の近似精度
- 損益分岐スコアの二分探索（100 位ラインをちょうど超える点 / 既に超えている場合 / 理論値でも届かない場合）
- σ→0 で期待値が決定論的な増分に一致すること
- 届かない譜面の期待値が 0 になること
- 能力が高いほど同じ譜面の期待値が大きくなること
- 自己ベストを下回る引きで期待値がマイナスにならないこと
- コミュニティ最高スコアで期待値が頭打ちになること
- 達成確率が損益分岐点に対して単調に下がり、予測中央値ちょうどで 50% になること
- 達成率降順（同率なら期待値降順）に並ぶこと、差分を満たした所で打ち切られること、届かなければ全件返すこと
- 譜面効果があれば BASE、無ければ同ランク平均（RANK）に落ち、下の段ほど σ が大きいこと
- θ_u が立たなければフォールバック予測を出さないこと

`AdditiveModelTest` は加法モデルの交互平均が、疎な合成データから θ_u + δ_c を復元できることを押さえている。
